# 검증 렌즈 설계안 — 비판적 사고 프레임워크를 파이프라인 모드에 적용하기

작성 2026-09-30. 입력: 파이프라인 모드(2026-09-29 구현), 사용자 첨부 "비판적 사고 프레임워크 조사 및 적용 방안"(SIFT·CRAAP·Paul-Elder·Six Hats·RAVEN·Bloom·CFF·SCREEN).

## 1. 전제: 두 종류의 인지 부하

첨부 문서는 **사람이** AI 결과를 검토할 때의 과부하를 다룬다. 질서에서는 검토의 1차 주체가 **검증 모델**이고, 사람은 그 판정을 읽는 2차 주체다. 따라서 부하가 두 군데에 생긴다.

| 주체 | 과부하 양상 | 문서의 처방이 옮겨지는가 |
|---|---|---|
| 검증 모델 | 지시가 많을수록 항목당 깊이가 얕아지고, 앞 항목에 편중한다. 긍정·부정을 한 프롬프트에 섞으면 무난한 총평으로 수렴한다(아첨 편향). | 옮겨진다. "렌즈 분리 + 한 번에 하나" 원칙은 모델에도 그대로 유효하다. 패널 하나 = 렌즈 하나. |
| 사람 | 검증 패널 N개의 긴 판정문을 동시에 읽어야 한다. 어제 실측에서 판정 하나가 1,500자를 넘었다. | 옮겨진다. 판정을 고정 형식으로 짧게 받고, 앱이 요약 배지를 먼저 보여 준다(SCREEN의 S·Stop). |

결론: 프레임워크는 **프롬프트 설계(모델 쪽)**와 **결과 표시 설계(사람 쪽)** 양쪽에 나눠 적용한다.

## 2. 질서의 제약과 프레임워크의 궁합

- API·도구 호출 없음. 모델이 할 수 있는 것은 "읽고 쓰기"뿐이다. SIFT의 I·F·T(출처 조사·교차 확인·원본 추적)는 **검색이 되는 서비스**(Perplexity, Grok, 검색 켜진 ChatGPT)에만 실질적으로 맡길 수 있다. Claude·Gemini 웹은 기본적으로 검색 없이 답하므로 사실 렌즈보다 추론 렌즈에 맞다.
- 주입 텍스트 길이에 비용이 있다(Gemini DOM 삽입, 20,000자 절단). 템플릿은 짧아야 한다. Paul-Elder 8요소×9기준 같은 전체 적용은 문서도 금지하고 질서도 감당 못 한다.
- 검증 패널은 동시에 돈다. 문서의 "순차(🟡 다음 ⚫)"는 모델에게는 강제할 수 없고, **사람에게 보여 주는 순서**로 대신한다.
- 한 번 클릭에 고정 횟수 전송(지시문 §8). 단계가 늘면 전송 수가 늘므로 깊이 선택으로 상한을 둔다.

## 3. 프레임워크 → 렌즈 매핑

각 프레임워크에서 질서에 맞는 부분만 떼어 "렌즈"로 만든다. 렌즈 = 검증 패널 하나에 넣는 짧은 템플릿.

| 렌즈 | 출처 프레임워크 | 모델에게 시키는 일 | 권장 모델 |
|---|---|---|---|
| ⚪ 사실 | Six Hats 흰 모자 + SIFT + CRAAP(C·A) | 답변을 검증 가능한 주장 단위로 분해 → 각 주장에 대해 확인/반박/확인불가 표시, 출처·최신성 명시. 의견은 건드리지 않는다. | Perplexity, Grok, ChatGPT(검색) |
| 🧠 논리 | Paul-Elder 핵심 3 (Assumptions·Implications·Point of View) | 당연시한 전제 3개, 결론이 맞을 때의 함의, 빠진 반대 관점. 사실 여부는 판단하지 않는다. | Claude, Gemini |
| ⚫ 위험 | Six Hats 검은 모자 + Pre-mortem + 역방향 검증 | "이 답변이 틀렸다고 가정하고" 가장 그럴듯한 실패 이유부터 나열, "A이므로 B"에 대해 B가 아닌 사례 찾기, 과신 표현 지적. | Claude, Gemini |
| 🟡 강점 | Six Hats 노란 모자 | 유지해야 할 것 3개, 잘한 이유. 5줄 이내. 사람이 비판을 읽기 전에 균형을 잡는 용도. | 아무 모델 |
| 🟢 개선 | Six Hats 초록 모자 + SCREEN의 N | 위 지적이 맞다면 어떻게 고칠지, 다음 행동 1~3개. | ChatGPT, Gemini |
| 🔧 코드 4레이어 | 코드 검토 Layer 1~4 | 동작→보안→품질→유지보수 순서로, 레이어마다 체크리스트를 순서대로 처리(Checklist Anchoring). 레이어를 건너뛰지 말라고 명시. | Claude, ChatGPT |
| 🎭 편향 | RAVEN | 추천·의견 문장만 골라 이해관계·중립성·전문성 관점 지적. 보고서의 결론부에만 적용. | Claude |

빠진 것: 빨간 모자(직관)는 사람 몫이라 렌즈로 만들지 않는다. 파란 모자(프로세스)는 앱의 프리셋이 대신한다.

**같은 렌즈를 두 모델에 주는 경우**는 사실 렌즈뿐이다. SIFT의 "다른 출처 교차 확인"이 곧 두 검색 모델의 교차다. 추론 렌즈는 모델마다 다른 렌즈를 주는 것이 문서의 "렌즈 단일화" 원칙에 맞고, 어제처럼 두 모델이 같은 문장을 반복 지적하는 낭비를 없앤다.

## 4. 검토 유형 프리셋 (문서 §3·§6의 시퀀스를 패널 배치로)

프리셋 = 렌즈 배정 + 권장 모델 + 깊이. 워크스테이션으로 저장한다.

| 프리셋 | 검증 패널 구성 (왼쪽→오른쪽 표시 순서) | 근거 |
|---|---|---|
| 보고서·문서 | ⚪ 사실(Perplexity) → 🧠 논리(Claude) → ⚫ 위험(Gemini) | 문서 §3-1: 흰 모자 1차 필터 → SIFT → Paul-Elder 3 → 검은 모자 |
| 아이디어·기획 | 🟡 강점(Gemini) → ⚫ 위험(Claude) → 🟢 개선(ChatGPT) | 문서 §3-2: 긍정 먼저, 그다음 부정, 마지막 대안 |
| 코드 | 🔧 동작·보안(Claude) → 🔧 품질·유지보수(ChatGPT) → ⚫ 위험(Gemini) | 문서 §3-3: 레이어 분리, 한 번에 하나 |
| 빠른 검토 | ⚫ 위험(Claude) 하나 | 문서 §3-4: 1~3분, Point of View 하나 |
| 결론·추천 검토 | ⚪ 사실(Perplexity) → 🎭 편향(Claude) | RAVEN 적용 대상 |

표시 순서 규칙: 항상 긍정(🟡) → 사실(⚪) → 추론(🧠) → 부정(⚫) → 개선(🟢). 앱이 파이프라인 모드에서 검증 패널 열 순서를 이 규칙으로 정렬한다.

## 5. 깊이 (Bloom's를 실행 강도로)

| 깊이 | 검증 패널 수 | 판정 길이 | 추가 단계 | 전송 수 |
|---|---|---|---|---|
| 빠름 | 1 | 5줄 | 없음 | 2 |
| 표준 | 2~3 | 15줄 | 없음 | 3~4 |
| 심층 | 3~4 | 제한 없음 | 수정 단계(§7) | 5~6 |

깊이는 전송 바에서 고르고, 프리셋에 기본값이 붙는다. 깊이가 판정 길이를 정하므로 사람의 읽기 부하가 예측 가능해진다.

## 6. 판정 구조화 (사람 쪽 부하 처방, 성적표의 씨앗)

모든 렌즈 템플릿 끝에 같은 고정 블록을 요구한다.

```
=== 판정 ===
등급: 신뢰 가능 | 일부 수정 필요 | 신뢰 불가
지적: 심각 n / 보통 n / 경미 n
핵심: (한 줄씩 최대 3줄)
```

앱은 이 블록을 파싱해 비교 기록에 `verdicts[serviceId] = { lens, grade, counts, headline[] }`로 저장하고, 파이프라인 완료 시 전송 바 위에 **요약 카드**를 먼저 띄운다. 카드에는 패널별 등급 배지와 핵심 줄만 보이고, 원문은 패널에서 읽는다. 이것이 SCREEN의 S(Stop)를 앱이 대신 수행하는 방식이다. 사람이 답변 원문을 먼저 읽고 수용해 버리는 자동화 편향을 막으려면, 생성 패널을 파이프라인 중에는 흐리게 표시하고 요약 카드가 뜬 뒤 원문을 보게 하는 선택 옵션도 둘 수 있다.

파싱이 실패하면(모델이 형식을 어기면) 등급 "형식 불명"으로 저장하고 원문만 남긴다.

**사람의 판단이 함께 쌓여야 한다.** 모델이 낸 지적 건수는 "얼마나 시끄러운가"이지 "얼마나 정확한가"가 아니다. 요약 카드의 판정마다 한 번 클릭으로 `맞는 지적 / 틀린 지적 / 보류`를 남기고(`verdicts[serviceId].judged`), 이 값이 있어야 성적표가 정확도를 잴 수 있다. 판정이 쌓이기 시작하는 A 단계부터 이 클릭이 같이 들어가야 나중에 되돌아가 표시할 일이 없다.

## 7. 선택 단계: 수정 (심층 깊이에서만)

검증 판정들을 모아 생성 패널에 "다음 지적을 반영해 수정본을 작성하되, 동의하지 않는 지적은 이유를 밝히고 유지하라"를 보낸다. 문서의 N(Next)에 해당한다. 전송 1회가 추가되며, 심층 깊이에서만 켜진다. 생성 모델이 지적에 무조건 굴복하는 것을 막기 위해 "동의하지 않으면 유지" 조항이 필수다.

## 8. 하지 말아야 할 것

- 모든 프레임워크를 한 프롬프트에 쌓지 않는다. 지금의 기본 템플릿(사실·논리·누락·판정)은 렌즈 셋을 합친 "종합 렌즈"다. 품질 문제가 아니라 위치의 문제로, 렌즈 도입 후에는 검증 패널이 하나뿐인 빠른 검토에서 쓰는 종합 렌즈로 재배치한다. 패널이 둘 이상이면 종합 렌즈를 중복해 주지 말고 패널마다 다른 렌즈를 준다.
- 렌즈를 5개 이상 동시에 돌리지 않는다. 사람이 못 읽는다.
- 검색이 없는 모델에게 사실 렌즈를 주지 않는다. 그럴듯한 출처를 지어낼 위험이 오히려 커진다.
- 판정 블록 없이 자유 서술만 받지 않는다. 기록이 자산이 되지 않는다.

## 9. 구현 단계 제안

| 단계 | 내용 | 코드 영향 | 규모 |
|---|---|---|---|
| A. 렌즈 라이브러리 (구현 2026-09-30) | 내장 렌즈 7개 + 사용자 렌즈, 검증 패널마다 렌즈 배정(역할 칩 옆 렌즈 선택), 판정 블록 파싱·저장, 워크스테이션에 렌즈 배정 저장 | `verifyPrompt.ts`(렌즈 정의·파서), `roles.ts`(verify에 lensId), `pipeline.ts`(패널별 프롬프트), `stage.ts`/`workstations.ts`(저장), `PanelSlot.tsx`(렌즈 칩), `SettingsView.tsx`(렌즈 편집) | 중 |
| B. 프리셋·깊이·요약 카드 | 프리셋 5종 내장(워크스테이션 템플릿), 깊이 선택, 완료 시 요약 카드, 검증 패널 표시 순서 정렬 | `BroadcastBar.tsx`, 새 `VerdictCard.tsx`, `stage.ts` | 중 |
| C. 수정 단계 | 심층 깊이에서 판정 → 생성 패널 재전송 | `pipeline.ts` | 소 |
| D. 성적표 | 프리셋(렌즈)×모델 매트릭스: 맞는 지적 비율, 등급 일치율, 평균 심각 지적 수. 일정량 쌓이면 전송 바에 배정 "추천"(자동 라우팅 아님) | 새 `Scorecard.tsx`, 집계 함수(`src/lib/scorecard.ts`, Supabase 조회 또는 로컬 캐시) | 중 |

A만 해도 "모델이 알아서"에서 "방법론이 적용된 검증"으로 바뀐다. 단, 판정 채택 클릭(§6)은 A에 포함한다. B는 사람 쪽 부하를 줄이는 단계이고, C는 선택, D는 판정과 채택 기록이 수십 건 쌓인 뒤에 의미가 있다. 실기 검증에는 프리셋당 파이프라인 1회(전송 3~4건)가 필요하다.
