# 기능 확장·유료화 적절성 분석 (2026-09-21)

요청: ① 생성 모델 + 검증 모델 1·2 지정, ② API 키 연동, ③ 요청 내용에 따른 자동 모델 라우팅 → 추가 후 웹 서비스 유료화 적절성, 기타 기능 추천.

## 결론 먼저
- ①·③은 지금 구조(DOM 주입) 안에서 구현 가능. ②는 "선택 모드"로 붙이는 것이 맞고, 유료화를 하려면 ②가 전제 조건이다.
- **현재의 DOM 주입 방식은 유료 서비스로 부적절**하다. 각 AI 서비스 약관이 자동화 접근을 금지하고, 셀렉터가 사이트 개편마다 깨지며, 웹 SaaS 형태로는 기술적으로 불가능(타 도메인 DOM 제어 불가)하다.
- 유료화가 목적이면 **API/BYOK(사용자 키) 기반 데스크톱·웹 앱**으로 재설계해야 한다. 이 시장은 이미 붐비므로 차별점은 "검증 파이프라인 + 한국어 워크플로 + 개인 지식관리(KMS) 연결"에 두는 것이 현실적이다.

## 1. 생성 모델 + 검증 모델 1·2 지정
### 동작
1. 사용자가 패널마다 역할을 지정: 생성 1개, 검증 1~2개 (헤더 칩: 생성 / 검증1 / 검증2 / 제외)
2. 보내기 → 생성 패널에만 전송 → 응답 수집(이미 있는 observeResponse·Markdown 변환)
3. 검증 프롬프트 템플릿에 생성 응답을 끼워 검증 패널들에 전송 → 응답 수집
4. 결과 뷰: 생성 답 | 검증1 판정 | 검증2 판정 나란히, 비교 기록에 3개 응답과 역할 저장
5. (선택) 생성 패널에 "검증 의견을 반영해 수정" 3단계
### 구현 난이도
낮음. 기존 runBroadcast를 단계형으로 확장(대상 필터 + 후속 프롬프트). 새 파일 1~2개, 하루 분량.
### 주의
지시문 §8 "자동 반복 전송 금지"와의 관계: 사용자 클릭 1회에 최대 3단계 전송으로 **횟수가 고정**되고 각 단계가 화면에 보이므로 "반복 자동화"가 아니라 "체인"이다. 단계 수 상한과 취소 버튼을 둔다. 검증 프롬프트는 프롬프트 라이브러리에 두어 사용자가 고친다.

## 2. API 키 연동
### 장점
- DOM 주입의 근본 약점(셀렉터 깨짐, 로그인 유지, synthetic 이벤트 무시, 플랜 제한) 해소
- 구조화 출력·스트리밍·토큰 계량 가능 → 라우팅·검증 자동화가 정확해짐
- 약관 문제 없음 → 배포·유료화 가능
### 단점
- 사용량 과금. 구독을 이미 내는 사람에게는 이중 비용 (지시문의 "API 비용 0" 전제와 충돌)
- 웹 UI 전용 기능(ChatGPT 메모리, Claude 프로젝트, Gemini 확장, 웹 검색 UI) 일부는 API에 없음
- 키 보관·유출 관리 필요 (macOS Keychain, Windows 자격 증명 관리자)
### 권장
"서비스별 모드 선택"으로 추가: 기본은 지금처럼 웹 UI, 원하면 해당 서비스만 API로. API 패널은 네이티브 webview 대신 앱 자체 렌더(마크다운 뷰)로 표시. 라우팅 분류기·검증 요약 같은 **짧은 보조 호출**은 Gemini API 무료 등급이나 로컬 모델(Ollama)로 돌려 비용 0을 유지할 수 있다.

## 3. 요청 내용 기반 자동 라우팅
### 방식 3단계 (아래로 갈수록 정확·비용↑)
1. **규칙 기반**: 키워드·길이·첨부 유형으로 분류 (코드 → Claude·ChatGPT, 검색·최신 → Perplexity·Gemini, 이미지 → Gemini). 비용 0, 예측 가능.
2. **경량 분류기**: Gemini Flash 무료 등급 또는 로컬 모델에 "이 요청의 유형과 최적 모델 순위"를 물어 JSON으로 받음.
3. **학습형**: 비교 기록에 남긴 사용자의 응답 평가(👍/👎, 선택)로 서비스별 점수를 갱신해 순위에 반영.
### UX 원칙
자동 라우팅은 **제안까지만**. 보내기 전에 "이번 요청: 코드 질문 → 생성 Claude, 검증 ChatGPT·Gemini" 배지를 보여주고 사용자가 바꿀 수 있게 한다. 무음 자동 전송은 오작동 시 신뢰를 잃는다.
### 구현
1단계는 반나절. 2단계는 API 모드(②)가 있어야 함. 3단계는 비교 기록에 평가 컬럼 추가 후 누적 데이터가 생겨야 의미.

## 4. 유료화 적절성
### 웹 서비스(SaaS)로 유료화 — 부적절 (현재 방식 기준)
| 쟁점 | 내용 |
|---|---|
| 기술 | 브라우저 웹앱은 다른 도메인(chatgpt.com 등)의 DOM을 제어할 수 없다. 데스크톱 앱만 가능 |
| 약관 | OpenAI·Anthropic·Google 소비자 약관은 자동화·스크래핑 접근을 금지. 개인 사용은 사실상 묵인되나, 이를 파는 순간 계정 정지·법적 통지 위험이 사업 리스크가 된다 |
| 안정성 | 셀렉터가 개편마다 깨진다(이번 개발 중에도 5개 서비스가 각각 다른 방식 요구). 유료 고객에겐 즉시 지원 부담 |
| 로그인 | 패스키 불가, Google 팝업, 나이 확인 모달 등 온보딩 마찰이 크다 |
| 참조 서비스 | Omni AI Workspace 같은 제품이 있다는 것은 수요의 증거이지만, 같은 회색지대 위에 서 있다 |
### 유료화가 되려면 — API/BYOK 재설계
- 사용자가 자기 API 키를 넣고(BYOK), 앱은 오케스트레이션·비교·검증·기록 UX를 판다. 토큰 비용은 사용자 부담.
- 데스크톱(Tauri 그대로)과 웹 SaaS 둘 다 가능. 웹은 키를 서버에 두지 않는 클라이언트 직접 호출 구조가 안전.
- 경쟁: TypingMind, Chatbox, Msty, OpenRouter 기반 앱 등 다수. 가격대는 월 $5~15 또는 1회 $30~60.
- 차별점 후보: 검증 파이프라인(①)을 기본 워크플로로, 한국어 프롬프트 라이브러리, 비교 기록의 KMS 내보내기(Obsidian·My AI KMS), 팀 프롬프트 공유.
- 현실적 순서: 개인용 DOM 버전은 지금대로 쓰면서, API 모드를 붙여 6~8주 사용해 본 뒤 유료화 여부를 판단. 초기 가격은 1회 라이선스(₩29,000~49,000) 또는 월 ₩4,900 정도의 저가 구독이 진입 저항이 적다.

## 5. 추가 기능 추천 (우선순위)
| 순위 | 기능 | 이유 | 난이도 |
|---|---|---|---|
| 1 | 검증 파이프라인(①) | 이 앱만의 워크플로. 유료화 시 핵심 가치 | 낮음 |
| 2 | 응답 비교 뷰 | 패널 응답을 앱 안에서 나란히·diff·표로 보기. 지금은 각 사이트 UI에 흩어져 있음 | 중간 |
| 3 | 응답 평가(👍/👎·채택) → 개인 모델 성적표 | 라우팅 3단계의 데이터원. "어떤 질문엔 어떤 모델"이 쌓임 | 낮음 |
| 4 | KMS 내보내기 | 비교 기록을 Markdown/Obsidian 노트로 내보내기, My AI KMS 인제스트. 지시문 Phase 3의 "향후 KMS 인제스트 대비" 완성 | 낮음 |
| 5 | 프롬프트 템플릿 변수 | `{{주제}}` 같은 변수를 보내기 전에 채움 | 낮음 |
| 6 | 규칙 기반 라우팅(③-1) | 비용 0으로 시작 | 낮음 |
| 7 | API 모드(②) | 위 1·3·6을 정확하게 만들고 유료화의 전제 | 높음 |
| 8 | 비교 기록 검색·태그 | Supabase full-text로 과거 비교 찾기 | 중간 |
| 9 | 글로벌 단축키·빠른 입력창 | 어느 앱에서든 호출해 보내기 | 중간 |
| 10 | 다중 파일 첨부·이미지 붙여넣기 | 현재 파일 1개 제한 | 중간 |

## 6. 제안하는 진행 순서
1. Windows Day 1 검증 마무리 (진행 중)
2. 검증 파이프라인 + 응답 비교 뷰 + 평가 (2~3일) — 개인용 가치가 가장 큼
3. KMS 내보내기 + 프롬프트 변수 + 규칙 라우팅 (1~2일)
4. API 모드 설계 (BYOK, 키 보관, API 패널 렌더) — 유료화 판단 전 프로토타입
5. 4~8주 실사용 후 유료화 여부·형태 결정
